## Indexing and recovery operations

- Run the existing worker from the reviewed factory deployment anchor against a read-only, chain-bound archive. Keep its SQLite database and WAL on persistent storage attached to one active writer. A stale head, inconsistent receipt or log, interrupted range, or unresolved branch leaves the service delayed. Use overlapping retries for reads only. Wallet recovery resumes the existing request and hash and never submits automatically.
- An optional index witness cross-checks chain, head and exact block hashes at the indexer's verification boundaries. It provides a consistency check for L2 observation. An omitted event can be detected when its verified provisional receipt exists. Header agreement alone cannot establish log completeness. Configure the witness only after reviewing the providers' operational independence and audit event completeness through separate archive reconciliation. The shipping worker has no new provider configuration or production activation path.
- The index retains a normalized launch record with its chain, PoolManager, factory, complete PoolKey and PoolId, block and transaction hashes, and factory event log index. Keep this compact historical record for as long as the launch is published. Read and validate raw receipts on demand. Raw receipts, trace trees, calldata and provider response bodies are transient inputs. The database has no raw payload archive.
- Take snapshots with SQLite Online Backup into a fresh destination. Record the returned SHA-256 in a separate authenticated backup inventory. Protect the database, backups and logs with restricted access and at-rest encryption in any approved hosting environment. Set a backup cadence and expire backup generations according to the approved retention policy. Practice restoring to a fresh path with the expected deployment scope and digest, then replay before switching the worker and readers. SQLite backup integrity covers the file snapshot, while canonical replay verifies chain state. [SQLite Online Backup API](https://www.sqlite.org/backup.html)

```sh
cd apps/web
node --import tsx scripts/new-launchpad-backup.ts backup /absolute/new-snapshot.sqlite
node --import tsx scripts/new-launchpad-backup.ts restore /absolute/new-snapshot.sqlite /absolute/new-recovery.sqlite <recorded-sha256>
```

If the common ancestor is outside retained checkpoints, preserve the old database for investigation. Restore a known-good image and replay against the reviewed anchor, or rebuild from the factory deployment anchor into a separate database. Keep affected reads delayed until the replacement passes replay and identity checks. Exercise backup restoration, disk headroom and provider quotas before setting recovery and freshness targets.

Use a filesystem that supports SQLite locking and same-directory atomic hard links for backup publication. A database, its active WAL and immutable backup artifacts have different recovery roles. Copying a live database file by itself is insufficient. During migration, stop competing workers before pointing a reader or writer at the restored path.

Each index pass considers at most 256 blocks, 512 delivered logs and 128 distinct receipt transactions. The worker shrinks a busy range before fetching receipts. If one block still exceeds a cap, the worker stops delayed for operator investigation. Reorg search probes at most 16 checkpoint candidates and the store retains 32 rolling checkpoints. The span in blocks depends on how the worker advanced. Provisional launch rows are limited to 128 per scope and expire after 30 minutes. The normalized record is capped at 8 KiB and a verified backup image at 256 MiB. Activity reads use a 128-block window and stop if the provider returns more than 1,024 logs. Old activity cursors need a fresh first page. Use upstream transport limits as well as local processing caps. These limits describe bounded work, with no production throughput or recovery-time measurement.

## Settlement, observation and finality

Pin transaction, account, chain, router, full pool identity, canonical receipt and the exact successful PoolManager payout for a native sell. Archive nodes must serve historic code, block headers, logs, receipts and bounded `callTracer` results for recovery. Core historical contract reads require EIP-1898 block hashes with `requireCanonical`. Validate trace provenance, success, call identity and payout semantics. The receipt parser accepts at most 256 logs and 64 KiB of combined log data. The trace parser accepts at most 4,096 nodes and depth 64. The review proof store retains up to 10,000 compact proofs per scope, each at most 2 KiB and eligible for reads for seven days. Replay does not extend an existing proof's expiry. Expiry limits proof reads immediately. Run pruning on an approved cadence even during low activity, and cover snapshots in the same retention policy. Recheck canonicality before using a retained proof. [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898)

Missing or malformed traces, insufficient proof, different payouts, stale blocks, rate limits and interrupted proof writes keep settlement pending. A launch record, an ERC-20 log or a v4 swap event alone cannot prove a native transfer. Read-only reconciliation should use bounded retries with backoff. Restrict trace access to the service operator and collect failure metrics without storing raw trace bodies or credentials. The loopback run checks agreement between two clients of the same Anvil instance and marks it as simulated agreement. Independent mode enforces distinct named HTTPS origins, and production must separately verify provider ownership and upstream independence. [Geth callTracer](https://geth.ethereum.org/docs/developers/evm-tracing/built-in-tracers)

The five public reads separate rechecked L2 observation from L1 finality. A fork head or L2 tag establishes an L2 observation at most. Production finality requires review of chain-specific Nitro deployment and inbox bindings, evidence tying the exact L2 block to an accepted Ethereum batch, and an independently verified Ethereum finalized block. Persist the L2 block/hash, batch or inclusion reference, L1 chain/block/hash, provenance and verification time. Finality stays unverified when any part is unavailable or contradictory. This candidate has no active L1 verifier. Hosted routing and indexing for the eventual exact deployment and full guarded PoolKey remain unknown. [Robinhood transaction finality](https://docs.robinhood.com/chain/transaction-finality/), [Arbitrum Nitro](https://docs.arbitrum.io/how-arbitrum-works/inside-arbitrum-nitro)

For later verifier acceptance, use Nitro's `NodeInterface.findBatchContainingBlock` only to locate a candidate batch. Verify the reviewed Ethereum SequencerInbox delivery and its data availability evidence through an independent path. Check that the batch covers the exact L2 history and that its L1 block hash is still canonical and finalized. Exercise L1 reorgs, mismatched chains and missing historical blob or batch data before allowing any finality promotion. [Arbitrum batch lookup](https://docs.arbitrum.io/arbitrum-essentials/how-to-estimate-gas#checking-parent-chain-confirmations-and-batch-information), [Arbitrum data availability](https://docs.arbitrum.io/run-a-node/data-availability)
