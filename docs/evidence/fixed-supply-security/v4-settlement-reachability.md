# V4 settlement reachability

The 12 funding, graduation and LP-harvest `reentrancy-balance` findings remain high severity in the strict 4663 analysis. This review traces the admitted call graph and adds a regression for a public caller who can open the shared PoolManager lock. It found no reachable balance mutation during settlement under the checked runtime bindings. That disposition is internal and conditional on the exact deployment profile. [Task 049 findings](../fixed-supply/security-review.md) · [Task 049 profile](../fixed-supply/4663-profile.json) · [Current pinned source and runtime manifest](4663-profile.json)

## Call graph and settlement boundaries

- **Graduation.** The active curve verifies the terminal backing and sold inventory, seals trades and grants an exact allowance. The engine accepts calls from the factory-bound active curve, checks the fixed PoolKey, and initializes through the only enabled hook permission, `beforeInitialize`. The guard checks PoolManager and graduation-engine identities and performs no external calls. No swap, add/remove-liquidity or donation hook is enabled. After funding, the curve requires both exact asset deltas and the authenticated dust callback before publishing its position. [Curve settlement](../../../packages/contracts/src/RMTLaunchBondingCurveV1.sol#L317) · [Engine admission](../../../packages/contracts/src/RMTV4CurveGraduationV1.sol#L215) · [Initialization hook](../../../packages/contracts/src/RMTV4CurveInitializationGuardV1.sol#L12) · [PoolManager hook dispatch](https://github.com/Uniswap/v4-core/blob/59d3ecf53afa9264a16bba0e38f4c5d2231f80bc/src/libraries/Hooks.sol#L178)
- **Position funding.** The engine encodes only `MINT_POSITION` and `SETTLE_PAIR`. The pinned PositionManager uses `_mint`, without an ERC-721 receiver call. The PoolManager sends the unlock callback only to the calling PositionManager. The canonical guard has no enabled liquidity callbacks and the new position has no subscriber. `SETTLE_PAIR` synchronizes each currency, settles native ETH and pulls the fixed token through the bound Permit2. Token approval and transfer are inherited ERC-20 paths without application callbacks. The engine checks exact ERC-20/Permit2 allowance consumption, its own token balance, both manager balance deltas and the final original position. [Engine funding checks](../../../packages/contracts/src/RMTV4CurveGraduationV1.sol#L345) · [Token implementation](../../../packages/contracts/src/RMTLaunchCurveTokenV2.sol#L8) · [Pinned PositionManager mint](https://github.com/Uniswap/v4-periphery/blob/ad04c9f24a170accf5ea1b2836bbafd514537ca6/src/PositionManager.sol#L348) · [Pinned settlement resolver](https://github.com/Uniswap/v4-periphery/blob/ad04c9f24a170accf5ea1b2836bbafd514537ca6/src/base/DeltaResolver.sol#L37)
- **LP harvest.** While holding the engine's mutation lock, `collectLpFees` verifies the exact PoolKey and original token ID, checks owner, liquidity, NFT approval and subscriber absence, then snapshots uncollected fee growth. The only actions are a zero-liquidity `INCREASE_LIQUIDITY` and `TAKE_PAIR` to the immutable ledger. Its native receiver accepts only the pinned PoolManager and makes no calls. ERC-20 delivery uses the fixed token. The engine rechecks custody, liquidity, fee growth, allowances and both exact ledger deltas before recording claims. ## Shared PoolManager regression

An unrelated caller can enter the shared PoolManager unlock loop. The official nested `unlock` entry reverts with `AlreadyUnlocked` before PositionManager actions execute. For graduation, the guard may have accepted initialization earlier in that nested attempt, but the settlement revert rolls it back with backing, inventory and allowances. The regression leaves another project's pool funded, donates a balance of the second token to the manager before the snapshot, and shows that neither pre-existing asset is booked as the second project's liquidity. A top-level retry settles exactly the second project's increment. [Pinned PoolManager unlock](https://github.com/Uniswap/v4-core/blob/59d3ecf53afa9264a16bba0e38f4c5d2231f80bc/src/PoolManager.sol#L104) · [Funding regression](../../../packages/contracts/test/RMTV4SharedPoolSettlement.t.sol#L102)

The harvest regression funds two projects, swaps both directions, and attempts harvest from inside the shared unlock. Failure leaves both credits pending, manager balances intact and the original position unchanged. A top-level harvest pays the expected ETH and token amounts, leaves the sibling token balance unchanged, and retains the original NFT custody and principal. These native tests use the pinned PoolManager and stock PositionManager source with the repository's simple Permit2 allowance fixture. The 4663 fork evidence separately exercises the official deployed runtimes. [Harvest regression](../../../packages/contracts/test/RMTV4SharedPoolSettlement.t.sol#L143)

The hostile token fixture substitutes runtime code, and the hostile Permit2 and PositionManager fixtures bind deliberately faulty dependencies. Those tests establish that unexpected debits, approvals, reentry, refunds, custody and fee diversion fail closed. The pinned graph and the shared-lock regressions constrain when those injected paths can occur. If a dependency, subscription rule, hook flag, token runtime or settlement action changes, retest the affected graph and the strict deltas. The existing high findings remain subject to independent assessment. [Original hostile settlement tests](../../../packages/contracts/test/RMTV4CurveGraduationV1.t.sol#L426)

Both focused regressions passed with Forge 1.7.1 and checksum-verified solc 0.8.26. Run from the contracts workspace.

```sh
forge test --offline --use "$PINNED_SOLC" --match-contract RMTV4SharedPoolSettlementTest -vv
```
