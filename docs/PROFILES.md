# Launchpad profiles

Profiles are an optional account workspace, separate from transaction authority. This branch prepares local Auth, Firestore and Storage integration. Production profile activation and production data changes are not authorized by these files.

## Existing Firebase identity and data

Read-only authenticated Firebase CLI metadata identified the existing **robinhood-meme-terminal** project and **RMT Web** app. Its native default Firestore database is in `nam5`, Standard edition with the free-tier flag. Point-in-time recovery and deletion protection are disabled; neither setting was changed. [Inactive reuse target](../config/firebase/existing-project.json) contains public identifiers only. No production user documents, credentials, tokens or API keys were exported.

Before cleanup (`ffa0eb4b^`), the account bridge verified Privy identity tokens and used `rmt_privy_` plus the SHA-256 of the Privy ID as the Firebase UID. A verified email could recover an existing Firebase account, subject to an immutable `rmt_privy_uid` binding. `users/{uid}` stored schema-1 profile fields (`displayName`, `handle`, `bio`, terminal preferences), update timestamps and watchlist metadata. Old rules required server-issued `privy_verified` and `rmt_privy_uid` claims. No durable wallet-to-UID mapping or avatar-storage rule was found in that tracked implementation.

A wallet signature therefore cannot establish ownership of an old email/Privy account. The new integration must preserve those records and require authenticated linking before adopting an existing identity. Do not merge by nickname, submitted email or an unverified wallet field. Legacy community, referral, marketplace and terminal code is not restored.

A newly verified wallet can create its own deterministic `rmt_launch_4663_<lowercase-address>` Firebase UID and atomic wallet binding. This creates an account record, not another wallet. Repeated sign-in reuses that binding. A server-established `rmtLaunchWalletBindingsV1` record may explicitly link to an existing Firebase UID; the server does not infer that link from an email, name, or old Privy claim. Conflicting UID/address bindings fail with account-recovery status. Reusing a trusted UID preserves legacy Auth claims and `users/{uid}`; it does not import the old profile fields or silently merge two profiles. General Privy/email recovery and self-service legacy linking are not implemented in this branch.

Actual collection-name metadata confirms `users` and the historical community/referral namespaces still exist; document values were not queried. The live Firestore rules were last updated August 2, 2026, have SHA-256 `11b3e1c33a3b542c6c5f57c3ccc6e763f62a5dbcb5da374c5e0f503f9b0a195d` (34,960 bytes), require Privy binding for users, and differ from the pre-cleanup tracked file. There is no live launch-profile namespace rule or Storage rule release.

Cloud Billing read-only metadata reports billing **disabled**. A direct metadata GET for the SDK-configured bucket returns **HTTP 404: bucket does not exist**; a configured bucket name does not prove storage availability. Firebase's [current Storage billing requirements](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024) require Blaze for Cloud Storage, including new default buckets. Bucket-based avatars are therefore unavailable under the current no-upgrade boundary. The branch instead prepares bounded, server-only Firestore avatar records; enabling a Storage bucket is not a prerequisite for that path. No billing account, bucket or paid plan was enabled. Do not represent emulator uploads as a working hosted feature.

## Local verification

Use Node 22, the pinned package manager and Java 21 or newer. The official Emulator Suite runs Auth `127.0.0.1:9099`, Firestore `127.0.0.1:8080` and Storage `127.0.0.1:9199` under **demo-rmt-launch-profiles**. This demo identifier does not provision a Firebase project. No hosted service or external credentials are needed.

```powershell
pnpm install --frozen-lockfile
# Optional: local JRE directory when java is not on PATH.
$env:RMT_PROFILE_JAVA_HOME = '<local Java 21 home>'
node scripts/profiles/run-emulator-tests.mjs
pnpm --filter @rmt/launch-website build
pnpm test:profiles:server
pnpm test:profiles:http
pnpm test:profiles:browser
```

The harness fixes the demo project, validates loopback-only emulator bindings, removes production credential/configuration environment variables and starts no cloud resources. `--command '<test command>'` runs an additional server/browser suite under the same emulators. The host verification used a private portable Temurin JRE 21.0.13+9; its official archive SHA-256 was `2332c0b4cff6bed722da3567c91d5e47568bcba863fa4945d0a8d6fc76158628`. No global Java installation was changed.

The profile-only emulator rules permit an individual public-card read and the authenticated UID's own private-preferences read. Collection enumeration and browser writes are denied. Wallet bindings, username locks, nonces, sessions, budgets, avatar bytes and legacy records are server-only. The website itself uses same-origin account APIs, not direct Firebase browser SDK access. Direct Storage reads and writes are denied; the server decodes, bounds and re-encodes avatars and serves them through its bounded profile API. Admin SDKs bypass rules, so server validation and authorization tests are separate requirements.

The actual official-emulator rules suite passed four tests: public-document access without enumeration/mutation, private UID isolation, internal/legacy namespace denial, and Storage upload/read/metadata/delete denial for signed-out, matching and other accounts. Direct-upload probes include SVG and oversized bytes. This is rules evidence only; it does not substitute for the server's nonce, session, username race, sanitized-image and browser acceptance suites.

**These are emulator rules, not a drop-in replacement for the current live project's rules.** The published rules already implicitly deny direct SDK access to the new namespaces. No global recursive public allow was found; the existing unconditional public read is scoped to `communityRooms`. The server-mediated production path does not require adding public or owner SDK grants. Preserve the live rules and their existing users; any explicit additive namespace rules need review against the then-current published source and overlapping matches. Never replace that file with the emulator rules.

## Wallet and deletion boundaries

The implemented sign-in format is EIP-4361 over `personal_sign`: one standard 65-byte EIP-191 signature must recover the exact wallet address. MetaMask/Rabby injected providers are discovered without signing. Connection, message review and signature approval are separate owner actions. No transaction method, approval, gas payment, seed phrase or private key is involved.

An EIP-7702 delegated EOA can use this path when its wallet returns a normal signature from the original EOA. The account sign-in does not approve its delegation or authorize a transaction. ERC-1271 Safe account signatures, ERC-4337 contract-account validation, counterfactual accounts and remote WalletConnect connectors are not implemented. Existing Safe treasury fee-claim compatibility remains separate evidence. Chromium/WebKit synthetic-wallet coverage does not establish physical iPhone sign-in acceptance.

Public responses select wallet, chain, username, display name, bio, project links, avatar URL and timestamps. They exclude Firebase UID, private preferences, nonces, session records and CSRF credentials. Only the private authenticated session response carries its own preferences and CSRF token. Public profile text does not prove token ownership or safety; creator-to-project links come from the canonical new-engine registrations. HTTPS project links are displayed as external user-provided links and are never fetched server-side. Avatars accept bounded uploaded raster bytes only, strip metadata, and store a re-encoded WebP of at most 64 KiB in a separate server-only Firestore document. No remote avatar URL or Storage subscription is used.

Profile deletion requires the current session's CSRF token, a fresh wallet message specifically consenting to deletion, and separate confirmation. It removes this app's public profile, preferences, username reservation, avatar and indexed app sessions. It preserves a minimal identity/epoch tombstone to reject replay, the Firebase identity, legacy data and every blockchain/indexer record. Sign-in can establish a fresh profile afterward. Public material may already have been copied by visitors; deletion is not a claim to erase third-party copies.

The server suite includes six core tests and ten real-Firebase suite entries (including the suite parent), covering genuine custom-token exchange/session cookies, a separate Node process restoring the profile, single-consumption parallel proofs, wrong browser/domain/chain/expiry, CSRF, username contention, explicit linked-UID preservation, avatar byte/pixel bounds, logout write races, app-only deletion and bounded cleanup. Disabled handlers also verify that no Firebase Admin SDK modules load. A separate actual Next HTTP test verifies successful sign-in and six forged host/origin cases. Next internally normalizes `127.0.0.1` to `localhost`; only that internal emulator alias is allowed, with external Host, Origin, protocol and port still exact. Cloud binding is unchanged. Avatar responses use a 60-second cache with revalidation; already cached public images can remain briefly after removal. These results do not verify the inactive hosted provider/configuration or ERC-1271 wallets.

## Dependency and hosting boundaries

Firebase Admin `14.5.1` and Sharp `0.35.5` are server dependencies. Firebase CLI `15.36.0`, Firebase test SDK `13.4.0` and rules testing `6.0.0` are development-only. The production dependency audit reports no known advisories. Narrow pinned patches address newly observed `smol-toml`, `brace-expansion` and gRPC findings; no Solidity dependency or compiler input changes.

The full development audit still reports one high (`picomatch`, `GHSA-fc5q-39xc-vjpf`) and four moderate advisories in the Firebase CLI dependency tree. Its upstream advisory currently offers no patched picomatch range; the current 4.x release remains flagged. This CLI is used with repository-controlled test configuration and is not shipped to Netlify Functions. The finding is retained, not suppressed. Do not process untrusted CLI glob patterns. These JavaScript results do not clear the existing contract-analysis findings or release gate.

Two existing Netlify native rate rules are reused: 120 reads/minute per IP/domain across discovery and public profile reads, and 12 requests/minute for account mutation and production-preparation endpoints. Firestore transaction budgets independently bound sign-in and profile operations. Native enforcement may lag, is not a global quota, and deployment post-processing/429 behavior must be checked on the actual preview. These limits do not authorize production authentication.

Prefer a standard Linux build for production Netlify packaging. On this Windows host, the stock adapter build needs directory-symlink permissions and emits Windows separators/absolute junction targets in generated Lambda artifacts. The isolated preview packaging uses bounded directory junctions and normalizes only the generated bootstrap paths and dependency-link targets to their equivalent POSIX locations; application files and dependency contents are preserved. Failed packaging attempts are retained as evidence. This does not verify active Firebase or native image dependencies on the hosted platform: actual Linux-built Auth/session/avatar acceptance remains a production activation gate.
