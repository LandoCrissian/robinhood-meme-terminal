# CCFF00 Community Engine error/status codes V1

**Status:** PLANNING ONLY — FUTURE MACHINE-CLASSIFIABLE ERROR TAXONOMY

The goal is to keep provider exceptions, human-readable messages and release decisions separate. Future runtime/operator APIs should expose stable bounded codes while logging sanitized detail internally.

Exact TypeScript enum placement is deferred to implementation packages. Codes below define semantics, not today's runtime.

## 1. General rules

- Codes are uppercase stable identifiers.
- A code means one condition; do not reuse it for unrelated failures.
- Provider-specific raw error strings map into RMT codes.
- Public UI may show a friendlier message but preserves the underlying code in diagnostic/proof views when safe.
- Unknown internal exceptions become a bounded generic code, not leaked stack/provider response.
- Security-sensitive detail is server-log only and sanitized.
- `UNCERTAIN` transaction state is not equivalent to failure.

## 16. Public-safe reason mapping

Examples:

```text
COMMUNITY_MINT_NONZERO_NATIVE_VALUE
→ "This mint is not zero-price under Community Engine V1."

COMMUNITY_MINT_UNKNOWN_ADAPTER
→ "This mint contract is not yet an admitted automation type."

COMMUNITY_MINT_COLLECTOR_NOT_ELIGIBLE
→ "The Community Collector is not eligible for this mint stage."

COMMUNITY_MINT_GAS_POLICY_EXCEEDED
→ "The estimated network gas exceeds the Community Engine limit."

COMMUNITY_QUALITY_EVIDENCE_INSUFFICIENT
→ "The project did not meet the current curation evidence threshold."

COMMUNITY_RANDOMNESS_NOT_YET_AVAILABLE
→ "Allocation is waiting for the predetermined public randomness round."

CCFF00_DELIVERY_STALE_SEAT_OWNERSHIP
→ "The selected holder no longer owns an eligible Square from the committed preference set; repair is required."

RMT_PAY_NOT_CURRENTLY_SAFE
→ "The current wallet/payment path has not passed the RMT Pay compatibility gate."
```

Avoid accusatory language such as “scam” for policy rejection.

## 17. Error-code change control

Once an error code appears in a persisted/public proof or runtime API, do not silently change its meaning. Add a new code or version the schema.

During Packages A–G, codes may still be refined before production activation, but Codex PRs should explicitly report additions/renames so the final runtime taxonomy remains coherent.
