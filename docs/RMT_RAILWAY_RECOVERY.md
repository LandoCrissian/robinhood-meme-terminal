## Recovery gate

The volume is attached to the original service definition but the service is offline. Its reported usage exceeds the documented manual snapshot threshold of 50% for a 500 MB volume. Existing scheduled backups could not be listed. Railway restore creates and mounts a new volume in place of the original mount. Do not use that restore flow on the original service under the current scope. Confirm a read-only export or owner-approved, bounded access to the original PostgreSQL service without changing its mount. Never expose a new public PostgreSQL port for this recovery. [Railway backup behavior](https://docs.railway.com/volumes/backups)

1. Review the original service's Backups history, account plan, spend cap and remaining allowance. Preserve access to the exact original volume and verify its encryption and PostgreSQL major version. The image tag provides configuration evidence only.
2. Before applying candidate schema, take a consistent logical pg_dump from an approved private session with the matching PostgreSQL client. Use the site's credential manager and an encrypted owner-controlled destination. Record SHA-256, time, client/server versions and TOC. If access itself needs billable runtime, obtain a bounded authorization before starting it. Preserve utility roles and grants separately if required.
3. Run pg_restore --list and restore into an independent, isolated local PostgreSQL of compatible major version using --single-transaction --exit-on-error --no-owner --no-acl. Compare table counts, indexer_state chain 4663, factory binding, deployment start 10248855, schema version, next_block, matching sync_points hash at next_block − 1, receipt and log identities, and canonical count. Validate original role permissions through metadata. Preserve every original row and review any mismatch offline.
4. Keep the legacy worker stopped until backup and restore checks pass. Start only the reviewed worker with one replica, minimum confirmation depth 20 and server-only reader and database credentials. Allow only the worker's private service to write. Treat outages and disputed or deep reorgs as a fail-closed state for operator review. The original Postgres volume remains mounted in place.
5. Verify /ready from Railway and diagnostic /health separately. Check authenticated /historical-launches and exact token lookup for the two historical V6 receipts, checkpoint timestamps, stale state and L2 confirmation. Verify 401 without bearer. After catch-up, restart and confirm checkpoint continuation, and check restored count against the reviewed onchain factory state. Observe CPU, memory, storage growth, egress and RPC rate with a bounded budget before committing to monthly operation.

The nine table-data entries, stored cursor, block hash and registration transaction/log identity passed comparison. This rehearses the logical recovery procedure. ## Netlify read boundary and activation

The branch uses the existing HTTPS worker endpoint /historical-launches. The worker guards writes with a dedicated PostgreSQL session-level advisory lock and validates binding and durable state before backfill. Application /ready and /health retain separate responsibility. New histories only surface after verified receipts, coverage and checkpoints. Authentication, a global worker read budget and bounded database reads protect the backend. When the endpoint is down, Netlify serves the checked-in snapshot with its historical timestamp and stale label.

Netlify uses the existing three-second timeout, 64 KiB cap and 30-second in-process list cache. Exact-address lookups coalesce and cache against the list checkpoint. Successful public GETs can use a 15-second shared durable CDN cache, shortened near expiry. Query strings stay in the cache key, and HEAD, errors, and degraded index responses remain uncached. The route-bound Netlify rule uses a 120-request window per IP and domain per minute. The local Netlify CLI found and bundled the exact rule from the monorepo, and the manifest passed 16 matching and exclusion checks. Hosted enforcement and CDN HIT behavior must be checked on the intended deploy. The exact local production-style Next app used a TLS-verified loopback fixture with a synthetic bearer, served the indexed projection, fell back after an HTTP 503, and returned to the indexed projection after reconnect. Three authenticated backend reads were observed. Local Chromium and WebKit also passed desktop, emulated iPhone portrait and landscape, and 85 denied path/method checks per engine. No additional cache, database, function polling schedule or external rate-limit service is required. [Netlify native limits](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/)
